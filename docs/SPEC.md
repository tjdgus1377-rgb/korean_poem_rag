## 1. 목적과 범위

시담은 한국 근대시를 검색하고, 선택한 작품의 표현·상징·시대 배경을 원문과 외부 해설 근거로 설명하는 서비스이다. 이용자는 제목·시인·연도·주제로 작품을 탐색하고, 작품별 채팅과 선택 구절 해설 카드를 사용한다.

항목 1건은 시 작품 1편이다. MVP는 F2001~F2012 전체와 NF2001~NF2007을 포함한다. 작품 원문, 문서가 설명하는 해석, 자료를 종합한 가능한 해석을 구분한다. 자료에 없는 실제 창작 의도·역사적 인과를 확정하지 않는다. 문학 학습 서비스이므로 의료·금융 전문가 조언 면책은 적용 대상이 아니다.

F2013 직접 프론트엔드, F2014 MMR, F2015 RAG 전후 품질 비교, F2016 여러 출처 결합은 심화 요구사항이다. 현재 데이터의 출처가 다양하다는 사실만으로 F2016 구현 완료로 간주하지 않는다. 심화 기능은 별도 ISSUE·SPEC·테스트를 작성한 후 진행한다. 이번 작업은 설계 문서 작성이며 앱 구현·자동 테스트·배포는 포함하지 않는다.

## 5. 데이터와 검색 텍스트

### 5.1 원시 자료와 파생 자료

활성 CSV의 `id`를 서비스의 `poem_id` 문자열로 사용한다. 숫자형 ID와 `WS_...` ID를 모두 보존한다. 제목이 같아도 시인·본문·판본이 다르면 자동 병합하지 않는다. `poem_metadata_100.*`의 ID를 현재 CSV의 ID로 가정하지 않는다.

기존 원시 파일을 덮어쓰지 않고 다음 파생 자료를 작성하는 것을 후속 구현 계약으로 둔다.

- `data/derived/poem_search_records.jsonl`: 작품 검색 레코드
- `data/derived/poem_field_evidence.jsonl`: 연도·주제·이칭의 필드별 근거
- `data/derived/source_manifest.jsonl`: 출처·권리·실제 접근 범위·본문 해시
- `data/derived/collection_manifest.jsonl`: 검색어·후보·선별·캐시 상태

이 경로들은 계획이며 이번 단계에서 자료가 생성된 것은 아니다.

### 5.2 연도 규칙

| 필드 | 의미 |
| --- | --- |
| `reported_year` | 원시 CSV의 기존 값. null 허용 |
| `reported_year_kind` | first_publication / collection_publication / unknown |
| `first_publication_year` | 출처로 확인한 최초 발표 연도. null 허용 |
| `collection_publication_year` | 확인한 수록 시집 간행 연도. 최초 수록인지 따로 근거로 설명 |
| `written_year` | 별도 근거가 확인한 창작 연도. 없으면 null |
| `year_evidence_ids` | 필드별 근거 레코드 연결 |

단순한 ‘1920년대 시’, ‘발표 연도’는 최초 발표 연도 기준으로 검색하고 UI에 기준을 표시한다. 이용자가 ‘창작’ 또는 ‘시집 간행’을 지정하면 해당 필드로 필터링한다. 미확인 값은 숫자 0이나 다른 종류 연도로 대체하지 않는다. 연도 조건이 없는 탐색에서는 연도 미확인 작품도 검색 가능하다.

예: 「그날이 오면」의 현재 1949는 시집 간행 정보로 다루고, 1930 창작과 구분한다. 「못 잊어」의 현재 1925를 최초 발표로 확정하지 않는다. 근거를 재확인하기 전 파생 필드가 채워졌다고 간주하지 않는다.

### 5.3 주제 작성

작품별 `interpretation` 노트에서 핵심 정서·갈등·태도를 1~3개의 짧은 표현과 설명으로 정리한다. `theme_terms`, `theme_summary`, `theme_evidence_ids`, `theme_review_status`를 보존한다. 자동 초안은 검토 후 활성화한다. 작가 일반론만으로 ‘저항’·‘조국’ 등을 모든 작품에 붙이지 않는다. 서로 다른 독법은 관점별로 표시한다. 주제 미확인 작품은 임의 주제 대신 ‘주제 설명 미확인’으로 표시하고 주제 조건 확정 결과에서 제외한다.

### 5.4 작품당 텍스트 형식

```text
제목: 진달래꽃
시인: 김소월
최초 발표 연도: 1922년
주제: 이별의 정한과 떠나는 이를 보내는 화자의 태도
```

1922는 초출을 확인한 경우의 예시다. 최초 발표 미확인은 ‘최초 발표 연도: 미확인’으로 쓰고 확인된 시집 연도가 있다면 별도 줄에 적는다. 이칭도 확인한 경우만 추가할 수 있다. ID·URL은 연결용 메타데이터다. ID를 임베딩에 넣어 의미 검색에 의존하지 않는다. 시 전문은 근거 컬렉션에 보관한다.

## 6. ChromaDB 컬렉션과 색인

검색 본문(document)과 필터·출처용 메타데이터를 구분한다. 임베딩 모델·차원·설정·자료 해시를 색인 매니페스트에 기록하고, 서로 다른 임베딩 공간을 한 컬렉션에서 혼용하지 않는다. 모델 변경 시 별도 저장 경로에 재색인 후 전환한다.

### 6.1 `poems`

- 한 작품당 document 1건, ID `poem:{poem_id}`. 예: `poem:9000320`.
- document: §5.4의 검색 텍스트.
- 필수 metadata: `poem_id`, `title`, `author`, `metadata_source_url`, `text_source_url`, `theme_summary`, `theme_review_status`, `schema_version`, `content_hash`.
- 확인한 경우만 metadata 추가: `first_publication_year`, `collection_publication_year`, `written_year` (정수), `reported_year`, `reported_year_kind`, `theme_evidence_ids_json`, `year_evidence_ids_json`.
- Chroma 필터용 null은 필드 생략으로 표현하고, 목록·복합 근거는 직렬화 문자열 또는 별도 매니페스트에 둔다. 숫자 필터 필드에 ‘미확인’ 문자열을 섞지 않는다.
- 동일 ID upsert. 활성 목록에서 제거된 작품은 매니페스트 대조 후 색인에서도 제거한다. 초기 색인 후 건수 100을 확인한다.

### 6.2 `poem_evidence`

- document: 실제 확인한 전문·문서 본문·공개 초록 또는 출처에 연결된 근거 요약.
- ID 규칙: `{poem_id}:{source_id}:{chunk_index:04d}`. 예: `9000320:KAE_AZALEA:0001`.
- `source_id`는 동일한 원출처·판본에 대해 안정적이어야 한다. 신규 자료는 정규화 원출처와 판본의 해시로 생성하고 원래 URL도 보존한다. 검색어·현재 시각·무작위 값으로 ID를 바꾸지 않는다.
- metadata 필수: `poem_id`, `poem_title`, `author`, `source_id`, `source_title`, `source_type`, `source_url` 또는 `file_name`+`page_number`, `locator`, `document_type`, `evidence_role`, `content_origin`, `access_scope`, `usage_terms`, `rights_status`, `ingested_at`, `chunk_index`, `content_hash`, `schema_version`. 실제 수집 시각을 아는 경우 `collected_at`도 저장한다.
- `document_type`: poem_text / commentary / author_context / bibliography.
- `evidence_role`: interpretation / context_only. access_lead는 색인 제외.
- `content_origin`: original_text / abstract / curated_summary. 요약을 원문 전문처럼 표시하지 않는다.
- 수집 이력은 매니페스트에 저장하고, metadata에는 `search_query` 또는 `collection_run_id`로 연결한다. 기존 수동 수집은 `precollected`로 표시하며 검색어·수집일을 만들어 내지 않는다. 수집일 미상이면 상태와 최초 인입일을 구분한다.
- 같은 작가 문서를 여러 작품에 연결할 때도 작품별 ID를 사용한다. 작가 맥락이 작품의 직접 해설로 승격되지는 않는다.

### 6.3 청킹과 멱등성

외부 해설은 1000자·중복 200자로 시작한다. `0 <= overlap < chunk_size`를 검사한다. 짧은 시 전문은 가능하면 한 청크, 긴 시는 연·행 경계를 우선하여 분할한다. PDF는 페이지 위치를 보존하고 원문·초록·요약을 합쳐 단일 원문인 것처럼 만들지 않는다.

동일 자료·설정은 같은 ID로 upsert한다. 문서가 짧아지거나 청킹 설정이 바뀌면 해당 작품·출처의 이전 청크와 신규 청크를 비교해 남는 옛 청크를 제거한다. 공유 문서의 다른 작품 청크는 제거하지 않는다. 실패 시 이전 완료 색인을 유지하고 성공 매니페스트를 먼저 기록하지 않는다. 색인 수는 논리 작품 수·외부 청크 수를 구분하여 표시한다.

동일 작품·출처에 여러 노트가 있으면 위치를 보존한 하나의 출처 입력 단위로 묶은 후 청크 번호를 부여한다. 노트마다 0001부터 시작해 서로 덮어쓰지 않는다. 전문은 판본별 출처 ID를 사용한다.

## 7. 외부 자료 수집·권리·캐시

### 7.1 색인 자격

`source_manifest`는 원출처, 실제 접근 위치·범위, 권리 조건, 확인일, 확인 근거, 본문 해시를 보존한다. `rights_status`는 verified / pending / restricted로 구분하고 허용 범위 안의 verified 자료만 적재한다. 공개 열람을 자동 재이용 허가로 가정하지 않는다. 시 원작과 웹 해설·현대어 전사·이미지 등의 권리를 구분한다. 위키백과 자료는 기존 기록의 라이선스와 귀속 정보를 보존한다.

원문 대신 기존 `evidence_summary`를 넣으면 `curated_summary`로 명시하고 원출처와 locator를 연결한다. 직접 읽지 않은 논문 전문을 근거로 생성하지 않는다. 다음 파일은 외부 근거에서 제외한다: `interpretation_examples.jsonl`, `question_coverage_review.csv`, `interpretation_readiness.csv`, 검토 보고서, `archive/`, 생성한 답변·테스트 정답. 자료 목록 259건 전체를 읽은 해설 259편으로 표시하지 않는다.

### 7.2 기존 자료 우선과 추가 수집

1. 선택 작품의 전문·직접 해설·시인 맥락을 기존 데이터에서 확인한다.
2. 작품 자체 문서는 처음 색인할 때 확보해 항상 포함한다. 제목·시인·판본이 확인된 자료만 해당 작품 문서로 판정한다. 작가·시집 문서는 맥락으로 남긴다.
3. 질문의 구절·주제에 대해 관련 근거가 부족하거나, 명시적으로 외부 확인이 필요한 연도·판본 질문이면 P1으로 검색어를 추출한다. 질문의 핵심 구절과 근거가 대응하지 않거나 출처 유형이 맥락뿐인 경우 부족으로 본다. 유사도 수치만으로 충분성을 보증하지 않는다.
4. 작품 제목+시인 검색어를 반드시 추가하고, 캐시를 조회한다.
5. 후보의 ID·제목·요약·URL로 P2를 실행한 후 선택 문서의 본문을 받는다. 확인된 작품 자체 문서는 P2의 제외·짧은 길이·선정 수 제한보다 우선한다.
6. 동일 제목의 다른 작품을 저자·내용·판본으로 구분하고, 권리·본문 접근 자격을 확인한 뒤 청킹·색인한다.
7. 기존 근거와 합쳐 답변 검색을 수행한다. 추가 수집 실패 시 기존 근거의 범위에서 답하거나 확인 불가로 응답한다.

‘작품 자체 문서 항상 포함’ 규칙은 저작권·접근 제한을 무시하거나 존재하지 않는 문서를 만들라는 뜻이 아니다. 위키 작품 문서가 없으면 확인된 다른 직접 자료를 사용한다. 이용 가능한 직접 자료 자체가 없으면 결손과 이유를 표시하며 F2004를 통과 처리하지 않는다.

제한 환경에서는 PDF 13쪽에 따라 검증된 문서 묶음을 읽는 어댑터로 대체한다. 묶음 모드에서도 P1/P2 입력·출력과 선별 결과를 기록해 파이프라인을 검증한다. 단순히 기존 파일이 있다는 이유로 F2003/F2004를 완료 처리하지 않는다.

### 7.3 캐시·중복·호출 예절

- 캐시 키: 제공자 + poem_id + 정규화 검색어 + 검색 정책 버전. 한 검색어가 다른 작품에 잘못 재사용되지 않게 한다.
- 상태: in_progress / success / empty / failed. success와 정상 empty는 반복 수집하지 않는다. failed는 성공으로 저장하지 않고 제한된 재시도를 허용한다.
- 동일 검색어의 재사용 시 수집을 생략하되, 청킹 설정 변경에 따른 재색인은 저장 본문으로 수행한다. 설정 변경은 외부 재수집 사유가 아니다.
- 자동 TTL 재수집은 MVP에 넣지 않는다. 명시적 새로고침은 별도 작업으로 기록한다.
- URL 정규화·리다이렉트·source_id·본문 해시로 중복 확인. 판본 차이와 서로 다른 문헌의 상반된 해석은 제거하지 않는다.
- 출처별 호출 간격·robots.txt·정책을 확인하고 설정에 기록한다. 연락처를 포함한 식별 User-Agent가 필요한 어댑터는 값이 없으면 호출하지 않고 안내한다.
- timeout·재시도 횟수는 설정으로 제한하고 429의 Retry-After를 따른다. 새 수집과 실패 응답에 무한 반복을 하지 않는다.

## 8. 세 프롬프트의 계약

검색된 문서는 신뢰할 수 없는 입력 자료로 취급한다. 문서 안의 지시를 시스템 지시로 실행하지 않는다. 모델이 만든 URL·ID를 신뢰하지 않고 입력 목록과 대조한다.

### 8.1 P1 검색어 추출

역할: 한국 근대시 문헌 조사 전문가. 입력은 mode, 선택 작품의 ID·제목·시인·연도 상태, 사용자 질문과 기존 자료의 부족 영역이다. `external_search` 모드는 부가 설명 없는 JSON만 출력한다.

```json
{
  "poem_id": "9000320",
  "question_focus": "화자의 이별 태도",
  "search_queries": ["김소월 진달래꽃 작품 해설", "김소월 진달래꽃 화자의 태도"]
}
```

프로그램은 poem_id 일치·검색어 문자열 목록·길이 제한을 검사하고, 작품 자체 검색어가 빠지면 반드시 보완한다. 출력 파싱 실패는 수정 요청 1회 후 명시적 오류 또는 제목+시인 기본 검색어로 대체하고 이력을 남긴다.

F2011의 조건 탐색에는 같은 P1의 `item_search` 모드를 사용한다. 선택 작품은 없어도 되며 다음 구조를 출력한다. 연도 범위·연도 종류·시인은 허용값으로 검증하고 임의 코드나 DB 질의를 실행하지 않는다.

```json
{
  "title_query": null,
  "author": "김소월",
  "year_kind": "first_publication",
  "year_from": 1920,
  "year_to": 1929,
  "theme_query": "이별의 슬픔"
}
```

### 8.2 P2 후보 선별

역할: 한국 시 자료 선별 전문가. `document_selection` 입력은 작품·질문과 후보 ID·제목·URL·짧은 요약·출처 유형이다. 후보 전문을 받기 전에 관련성과 신뢰성·중복을 평가한다.

```json
{
  "selected_documents": [{"candidate_id": "candidate_01", "reason": "해당 작품의 화자 태도를 다룸"}],
  "rejected_documents": [{"candidate_id": "candidate_02", "reason": "다른 시인의 동명 작품"}]
}
```

입력 후보 ID만 허용하고 중복·동시 선택/제외를 거부한다. 적절한 후보가 없으면 selected_documents는 빈 배열이다. 본문 수집 후 작품 식별을 재확인한다. 확정된 작품 자체 문서 포함은 모델 선택보다 프로그램 규칙이 우선한다.

F2011에는 같은 P2의 `poem_selection` 모드로 작품 후보 ID·확인된 주제·조건을 입력한다. 출력은 `selected_poem_ids`와 ID별 짧은 조건 부합 근거다. 최종 시인·연도 필터는 프로그램이 다시 적용한다. 주제를 뒷받침하지 못하는 후보를 억지로 채우지 않는다.

### 8.3 P3 근거 기반 답변

역할: 문헌 근거를 사용하는 시 해설자. 입력은 작품·질문·작품별 이전 대화와 번호가 붙은 근거 목록이다. 각 근거에는 출처 유형, 본문 종류, 접근 범위, locator를 표시한다. 이전 답변을 새로운 외부 근거로 삼지 않는다.

일반 답변 출력은 한국어 Markdown이다. 근거가 있는 주요 주장 뒤 `[근거 1]`, `[근거 1, 2]`를 붙인다. 인용문·가능한 해석·자료의 견해·확인된 사실을 구분한다. 관련 근거가 없으면 ‘제공된 자료에서는 확인되지 않습니다.’라고 답한다. 자료에 명시된 부분과 종합한 추론을 구분하며 해석을 하나의 정답이나 시인의 실제 의도로 확정하지 않는다.

구절 해설 카드 모드는 같은 P3에 작업 종류를 전달하고 다음 제목을 가진 Markdown을 출력한다: 선택 구절 / 표현 / 가능한 해석 / 배경 / 근거와 한계. 각 항목에 자료가 없으면 확인 불가를 적는다. 출처 제목·URL은 모델 생성값을 사용하지 않고 실제 인용 번호와 저장 출처를 대조해 화면에 표시한다.

## 9. 실행 흐름과 검색

```text
자료 검증 → 주제·연도 근거 정리 → 두 컬렉션 초기 색인
작품 탐색·선택 → 기존 자료·캐시 확인 → 부족 시 P1/P2 수집·추가 색인
→ LangGraph retrieve → generate → 인용 검증·표시 → 작품별 대화 저장
```

수집 준비는 그래프 호출 전에 수행한다. 답변 그래프는 PDF 요구대로 retrieve와 generate 두 노드를 둔다. 노드 사이 상태에는 poem_id, question, mode, selected_quote, evidence 목록, answer를 포함한다.

retrieve는 작품 메타데이터를 ID로 정확히 조회해 반드시 넣고, poem_evidence를 poem_id 필터와 질문 임베딩으로 검색한다. 메타데이터가 없으면 다른 작품의 유사 결과로 대체하지 않는다. 외부 Top-k 기본 5이므로 일반 근거 예산은 메타데이터 1건 + 외부 최대 5건이다. 같은 ID 또는 같은 출처·locator·동일 본문 해시 청크만 중복 제거하고 서로 다른 출처는 단순 문구 유사성만으로 합치지 않는다.

구절 질문은 원문에서 그 구절을 포함하는 청크를 외부 근거 예산의 예약 슬롯으로 우선 배치하고 나머지를 의미 검색한다. 긴 작품을 잘랐을 때 질문 구절이 빠지지 않게 한다. 작가 맥락은 동일 작품에 연결된 것만 검색하며 맥락만으로 직접 구절 뜻이 확인되었다고 처리하지 않는다.

generate는 번호가 고정된 근거 목록을 P3에 전달한다. 같은 답변 내 번호는 바꾸지 않는다. 긴 문맥은 입력 토큰 예산에 맞춰 근거 단위로 제한하고, 선택 구절·작품 메타데이터·해당 출처 위치를 보존한다. 초과 자료를 사용한 것처럼 인용하지 않는다.

## 10. 화면과 이용자 동작

### 10.1 탐색·선택·대화

사이드바에 작품 목록과 두 컬렉션 건수를 표시한다. 자연어 조건 탐색은 P1 조건 추출→확인된 연도·시인 필터+의미 검색→P2 후보 선별→정확 조건 재검사를 거친다. 결과 카드에 제목·시인·연도 종류·주제·부합 이유를 표시한다. 결과 없음은 ‘조건에 맞는 작품을 찾지 못했습니다.’로 안내한다. ‘발표 연도’ 검색의 기본 기준을 최초 발표로 표시한다.

선택 결과는 동일 작품 ID의 대화로 이어진다. `messages_by_poem_id` 형태로 작품별 대화와 당시 근거 스냅샷을 세션에 보존한다. A→B→A로 이동해도 이전 A 대화와 인용이 복원되어야 한다. MVP는 현재 브라우저 세션 보존이며 로그인·장기 계정 저장은 범위 밖이다.

### 10.2 선택 구절 해설 카드

선택된 작품 전문의 구절을 지정하고 ‘구절 해설’ 동작을 실행한다. 선택 구절이 표시 판본에 실제 존재하는지 검사하고 필요하면 공백 정규화 후 대조한다. 존재하지 않으면 다시 선택하도록 안내하고 다른 작품 구절로 해설하지 않는다. 결과는 표현·가능한 해석·배경·근거·한계를 갖춘 별도 카드로 표시하고 P3 및 동일한 출처 표시 규칙을 따른다.

### 10.3 근거·진행·오류

답변의 `[근거 N]`에서 현재 목록 범위 내 번호만 추출하고, 실제 인용된 출처만 표시한다. 제목·출처 유형·원문 URL 또는 파일명과 쪽·locator·초록/요약 여부를 함께 제공한다. 동일 문서가 여러 번호에 있으면 관련 번호를 묶어 표시할 수 있다. 과거 답변도 당시 근거 목록으로 다시 그린다.

인용이 없으면 ‘답변에 인용된 근거가 없습니다.’를 표시한다. 존재하지 않는 번호가 나오면 1회 수정 요청 후에도 실패할 경우 해당 답변을 근거 확인 실패로 표시하고 출처가 검증된 답변처럼 제공하지 않는다. 정확한 번호가 존재하는지와 그 근거가 주장을 실제 지지하는지는 별도 평가한다.

상태는 기존 자료 확인 / 검색어 추출 / 후보 선별·수집 / 색인 / 근거 검색 / 답변 생성 / 완료로 구분한다. 색인 없음, 키 없음, 모델 연결 불가, 외부 timeout·429, 검색 없음, 해설 근거 부족을 각각 안내한다. 키·전체 프롬프트·stack trace·개인 연락처는 화면에 표시하지 않는다.

## 11. 설정·모듈·성능

초기 설정 계약(아직 설정 파일 구현 아님):

| 키 | 초기값·규칙 |
| --- | --- |
| `chunk_size`, `chunk_overlap` | 1000, 200자 |
| `evidence_top_k` | 5, 작품 메타데이터 1건과 별도 |
| `search_type` | similarity. MMR은 심화 선택 후 |
| `collection_mode` | existing_first |
| `selection_limit` | 일반 후보 최대 5건, 작품 자체 문서는 제한 예외 |
| `request_timeout_seconds`, `max_attempts` | 30초, 총 3회 이내. 어댑터 정책과 전체 시간 예산 고려 |
| `index_path` | 실행 환경별 로컬 경로. 자동 커밋 금지 |
| 모델·API 키·연락처 | 환경변수. `.env.example`에는 변수명과 빈 값만 |

Python과 라이브러리 버전은 PDF 5~6쪽 및 현재 requirements를 기준으로 설치 호환성을 먼저 확인한다. 설치 실패 시 임의 업그레이드하지 않고 변경 이유·영향을 SPEC/ISSUE에 기록한다.

권장 책임 경계는 `data_preparation`, `collectors`, `indexing`, `retrieval`, `prompts`, `pipeline`, `ui`이다. 이름은 구현 ISSUE에서 확정하되 UI에서 수집·색인 코드를 직접 중복 구현하지 않는다. 기존 `step7_skeleton.py`를 진입점으로 발전시키며 필요한 함수를 모듈로 분리한다.

NF2001은 PDF에 수치가 없으므로 최초 실측을 바탕으로 후속 ISSUE에서 첫 질문·캐시 질문의 지연 예산과 실행 환경을 정한다. 측정은 전체 시간과 P1·검색·P2·본문 수집·색인·retrieve·generate를 구분한다. 지연 예산 확정 전 ‘성능 통과’로 표시하지 않는다. 외부 수집이 오래 걸리면 진행 상태와 실패 복구를 제공하며, 시간 초과를 숨겨 성공으로 기록하지 않는다.

## 12. 테스트·검증 전략

### 12.1 SPEC과 TDD

각 구현 ISSUE는 위 AC와 테스트를 연결한다. SPEC 커밋→실패 테스트 기록→최소 구현→통과→리팩터링 순서를 지킨다. 테스트는 검증하려는 동작 때문에 실패해야 하며 환경 미설치만으로 Red를 충족했다고 하지 않는다. 순수 문서 변경은 문서 구조·링크·요구사항 누락 점검으로 검증하며 억지 기능 테스트를 만들지 않는다.

단위·통합 테스트는 고정 fixture와 가짜 LLM/HTTP·임시 Chroma 저장소로 재현한다. CI에서 유료 API·공개 인터넷 응답을 필수 의존성으로 두지 않는다. 실제 GMS·임베딩·외부 수집 smoke와 브라우저 E2E는 별도 실행으로 증거를 남긴다. 모의 테스트만으로 실제 서비스 응답 품질을 통과 처리하지 않는다.

### 12.2 핵심 검증 사례

- T01: 제목/시인/주제 텍스트 구성, 100편 ID 연결, 연도 빈칸·초출/시집 구분, 이전 ID 혼입 방지.
- T02/T05: 두 번 색인, 공유 출처의 작품별 ID, 재청킹 후 옛 청크 제거, 짧은 원문 보존.
- T03/T04: JSON 오류·후보 ID 위조·작품 자체 문서 제외 시도·동명 작품·정상 empty 캐시·실패 재시도·연락처 누락·429.
- T06/T07: 메타데이터 무조건 포함, poem_id 격리, Top-k 변경, 질문 구절 원문 포함, 근거 없음·상충 해석·문서 내 지시 무시.
- T08~T12: 실제 인용만 표시, 잘못된 번호, 과거 근거 복원, 작품 전환, 연도 조건 오탐 제거, 유효/무효 구절 카드, 비밀값이 든 예외 주입 시 화면 미노출.
- T13~T16: 단계별 지연, 민감정보, 모듈 경계, access_lead·생성 예시·권리 미확인 자료의 색인 제외.

### 12.3 E2E와 제출 증거

환경 설치·앱 실행 확인→실제 브라우저 조작→제목·시인·연도·주제 탐색→작품 선택→질문·구절 카드→원문 링크·인용→다른 작품으로 이동·복원→근거 부족·키/색인 없음 확인 순으로 수행한다. 시크릿 없는 스크린샷과 테스트 결과를 PR 및 검증 산출물에 첨부한다. 명령 실행만 하고 실제 화면 확인 없이 E2E 완료라고 하지 않는다.

PDF 18~19쪽 체크리스트의 통과 / 실패 / 미확인을 구분하고, 셀프 점검·옆 교육생의 상호 점검은 별도로 기록한다. 실제 사람이 수행하지 않은 상호 점검을 대리 완료하지 않는다. LangGraph 구조, 두 번 색인 수, 후보 선택/제외, Top-k·청킹 변경 전후 화면도 증거 대상이다.

### 12.4 품질 비교 확장 준비

F2015 선택 시 최소 5개의 대표 근거 질문을 고정하고, 사실 정확성·근거 제시·모름 처리로 RAG 전후 답변을 비교한다(PDF 19쪽). 같은 모델·질문·생성 조건을 기록한다. 검색 평가는 제목·시인·오탈자·이칭·구절·연도·주제·동명/판본을 포함하고 Recall@k·MRR·명시 조건 정확성을 사용한다. 답변은 허용 가능한 해석·필수 근거·단정 금지 범위를 평가하며 생성 예시를 근거 색인에 넣지 않는다. 평가 데이터와 판정 기준을 먼저 SPEC에 커밋한 뒤 기능을 구현한다.

## 13. 개발 흐름·산출물

ISSUE와 SPEC 작성 → `codex/` 작업 브랜치 생성 → SPEC 커밋 → 실패 TEST → 구현 → PR → CI → 통과 후 리뷰 에이전트 리뷰 → 지적 사항 수정·필요 재검증 → 리뷰와 필수 검사 통과 후 머지 → ISSUE 종료.

현재 GitHub ISSUE 생성은 연결 앱의 403(Resource not accessible by integration)으로 실패했다. `docs/issues/SPEC-001.md`는 게시할 본문을 가진 로컬 초안이며 원격 ISSUE로 가장하지 않는다. 접근 복구 후 기존 ISSUE 여부를 확인하고 게시·연결한다. 이 설계 단계에서는 PR·CI·리뷰·머지·ISSUE 종료를 수행한 것으로 표시하지 않는다.

후속 제출 산출물은 요구사항 정의서, RAG 파이프라인 설계서, 소스, 실행 README, 요구사항 대조표·테스트 결과·셀프/상호 체크리스트·스크린샷이다(PDF 21~23쪽). 실행 결과가 생기기 전에는 설정 선택의 효과나 성능 개선을 확인한 것처럼 쓰지 않는다.

## 14. 구현 ISSUE 분할안

1. 활성 자료 어댑터·연도 분리·주제 근거 검토·권리 매니페스트 (F2001, NF2007).
2. 작품/근거 청킹·Chroma 색인·멱등성·설정 (F2002, F2005).
3. P1/P2·기존 자료 우선·추가 수집·캐시·외부 API 예절 (F2003, F2004, NF2002, NF2006).
4. 작품별 retrieve/generate·근거 병합·답변·인용 (F2006~F2008).
5. 작품별 채팅·조건 탐색·구절 해설 카드·오류 안내 (F2009~F2012).
6. 통합·실제 브라우저·성능·보안 검증·CI·제출 결과 정리 (NF2001~NF2005, PDF 4·6장).

각 ISSUE의 SPEC과 실패 테스트를 먼저 작성한다. 전체 계획을 한 번에 완료로 표시하거나 다른 사람이 편집 중인 데이터·제출 파일을 임의로 커밋하지 않는다.
