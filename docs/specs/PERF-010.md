# 측정 기반 응답 지연 개선 — ISSUE #10

관련 NF2001/F2003~F2006. 근거 없는 ‘최대34초’ 장애를 기록하지 않는다. 현재 실제 질문 측정은 E2E-007과 IDENTITY-009에 있다. 전체 지연 목표는 미확정이므로 보편적인 SLA 통과를 주장하지 않는다.

## 확인한 비용

같은 공개 질문의 P1만 실제 GMS에 연결하고 문서 HTTP는 고정 빈 어댑터로 분리했다. 첫 호출1.922초, 같은 질문 반복3.703/1.297초였으며 P1이1.875/3.672/1.265초를 차지했다. 기존 HTTP 캐시 앞에서 매번 P1을 호출해 모델 표현에 따라 검색어도 바뀌었다(누적 LLM1/2/3회·고정 검색3/5/6회). 이는 전체 실시간 수집 응답 측정이 아니라 P1 병목 분리 실험이다. 이를 근거로 동일 질문의 검증된 검색 계획 재사용을 구현한다.

## 변경·인수 조건

AC-P1: 기존 SQLite에 로컬 검색 계획 캐시를 둔다. key는 질문 원문(앞뒤 공백 제거)·poem_id·제목·시인·채팅 모델·P1 프롬프트 버전의 해시다. 다른 작품/질문/모델/버전은 재사용하지 않는다. 유효한 검색어 목록만 저장하고 ModelError·형식 오류는 저장하지 않는다. 기존 문서 success/empty 재사용과 failed 재시도는 유지한다. 계획 캐시가 존재해도 실패한 HTTP는 다시 시도한다.

AC-P2: 새로운 허용 문서 여러 건은 `sync_sources` 한 번으로 배치 색인한다. 기존 출처를 보존하고 해당 작품의 변경 청크만 정리한다. 정책 검증과 poem_id 범위를 유지한다.

AC-P3: 실제 GMS P1+고정 HTTP의 같은 질문 first/followup 측정을 동일 조건에서 반복하고 LLM 호출 수·단계 시간을 기록한다. 차이가 공급자 지연/워크로드에 영향을 받는다는 한계를 명시한다. 시 전문·답변·검색어 원문을 로그로 공개하지 않는다.

AC-P4: 질문 전체 측정 CLI는 기존 모델/자료/기준 색인을 사용하며 first/followup·수집 단계·retrieve/generate/total을 분리한다. 실행 결과는 로컬 `evaluation/runs/`에 저장한다. 초기 색인 시간은 질문에 섞지 않는다. 기존 단계가 생략되면0으로 표시한다. 자동 테스트에는 가짜 LLM/HTTP·임시DB를 쓰고 의미 품질을 성능 지표로 대신하지 않는다.
